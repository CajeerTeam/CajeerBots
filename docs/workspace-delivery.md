# Workspace delivery bridge v1 (compatibility patch for CajeerBots 1.0.2)

Install all files from the compatibility patch on the exact CajeerBots 1.0.2 source. Stop API, bot runtime, worker, scheduler and CLI jobs before rebuilding; do not mix old and new workers. No Prisma schema change is necessary: the patch uses the native `bot_outbound_messages` table and a reserved `workspace-` ID prefix. Configure both API and worker with the same `WORKSPACE_BOT_TARGETS` JSON, e.g. `{"API_KEY_ID":{"communityId":"COMMUNITY_ID","accountId":"ACCOUNT_ID","provider":"telegram","channelId":"-100123456789"}}`. One configured target per key. Do not give the key other permissions; create it with exactly `workspace:messages` and `community:COMMUNITY_ID`. API accepts only API keys, not JWT or global/bootstrap keys. `channelId` is a string: Telegram group/supergroup/channel using `-100…`, VK positive peer ID. Ensure bot membership, posting permissions, and token references in Bots before enabling. Discord is not supported by this bridge.

API prefix `/api/communities/{communityId}/bot-runtime`, header `x-api-key`. Private opt-in bridge surface (not a replacement for the general versioned OpenAPI/SDK):

- `GET /workspace-target` returns `api: workspace-delivery-v1`, `credentialId`, `communityId`, `accountId`, `provider`, `channelId`, and `revision` (bot account `updatedAt`, ISO UTC with milliseconds).
- `PUT /workspace-messages/{id}` accepts exactly `accountId`, `channelId`, `revision`, `text`. `id` is `workspace-` followed by 32 lowercase hexadecimal characters, text plain UTF-8, max 2000 Unicode code points and 8000 bytes. An identical request uses the existing row; changed content, owner or destination is rejected. A successful receipt means queued/known, not necessarily sent.
- `GET /workspace-messages/{id}` returns a receipt only for the key's own allowlisted destination. `POST /workspace-messages/{id}/cancel` cancels if pending or verified preflight failure. `POST /workspace-messages/{id}/retry` retries only verified preflight failure, max eight claims total. No automatic retry of an ambiguous provider request. Neither operation can resurrect sent or uncertain messages.
- Receipt: `id`, `communityId`, `accountId`, `provider`, `channelId`, `revision`, `sha256` (UTF-8 text), `status`, `attempts`, `providerMessageId` (null until sent). Status: `pending`, `sending`, `sent`, `retryable`, `cancelled`, `uncertain`. A worker crash after claim is `uncertain` once its five-minute lease elapses, even if no request actually went out. Provider errors after the send boundary are always uncertain. Provider receipt is not proof of recipient reading the message.

The API validates the account and target; before contacting Telegram/VK the native worker validates current API-key grant, account revision, allowlist, token reference and message. Standard retry, scheduler recovery and bot runtime retry exclude these IDs. Revoking a key or disabling its allowlist stops new claims that have not crossed the provider boundary; it cannot undo an already started call. Do not manually modify or delete these rows, restore an older database or start an unpatched worker while any message may have been handed off. Back up the database and reconcile with provider history first. A changed account revision requires a new preview (cancel unsent old row first). A rotated token under the same reference is not a new account revision. Key-ID replacement/target remapping requires coordinated operator migration; do not transparently replay historical deliveries with a new key.

Build and verify: `pnpm install --frozen-lockfile`, `pnpm build`, `pnpm typecheck`, `pnpm test`. Run API + worker together with the patched build, then send a harmless test message to an authorized test channel through Workspace. Test cancel, safe preflight failure and status; inspect provider history for duplicate-free delivery. Do not interpret unit tests as live-provider acceptance.
